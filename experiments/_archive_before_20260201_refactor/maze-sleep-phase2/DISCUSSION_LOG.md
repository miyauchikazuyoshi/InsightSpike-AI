## 1. 最初の問い：バイアスはエッジかノードか？

### 問題提起

> 迷路のsleepモードでの実装のバイアスって、エッジにかけるべきなのかな、ノードにかけるべきなのかな。

### 検討

geDIG理論の観点から：
- Phase 1-4 はエッジ操作が中心
- ノード操作は Phase 5（仮説ノード生成）

迷路での意味：
- ノード = 状態（位置）
- エッジ = 遷移（状態s から行動a で状態s'へ）

### 結論

理論的には**エッジベース**が正しい。ただし、現在の実装では：
- ノードID = (x, y, direction) = 「位置から方向への遷移」
- これは実質的にエッジの情報を持っている

## 2. 「同じ/違い」の認識問題

### 問題提起

> 2回目に迷路を解く時、エージェントは自分がいる場所が、過去に経験していると気づけているんだろうか。

### 検討

現在の類似検索：
- 「似ている」ノードを返す（連続的な類似度）
- しかし「同じ」という認識が明示的でない

必要な区別：
```
再認 (Recognition): 「これは前に来た場所だ」
  → 過去の経験をそのまま適用

想起 (Recall): 「これに似た場所があった」
  → 過去を参考に推論
```

### 認知科学との接続

予測符号化 (Predictive Coding)：
```
予測誤差 ≈ 0  → 「既知」→ 情報を取り入れない
予測誤差 > 0  → 「新規」→ 情報を取り入れる
```

AG/DG との対応：
- AG: 予測誤差が大きい → 注意を向ける
- DG: 記憶すべきと判断 → グラフに統合

## 3. ベクトル形式への疑問

### 問題提起

> ベクトルの形式もこれでいいのかっていう小骨。

### 現状の8次元ベクトル

```
[row, col, dx, dy, passable, visits, outcome, purpose]
 位置      方向     属性       ラベル
```

### 再解釈：特徴 vs ラベル

```
構造特徴（類似度計算用）: [0-5]
ラベル（評価用）: [6-7]
```

### 結論

ベクトル形式自体より、「識別子」と「特徴」の分離が重要：
- 識別子（離散）: node_id で「同じ」を判定
- 特徴（連続）: vector で「似てる」を判定

## 4. インデックス + グラフが本質

### 洞察

> faiss的なindexだけでもいいのかもな。。むしろindexとグラフ構造こそ本質なのかも

### 整理

```
インデックス: 「これは何か？過去に見たか？」（識別）
グラフ構造:   「これに関連するものは何か？」（関連）

ベクトルは手段。本質はインデックス + グラフ。
```

## 5. インデックスの仕組み調査

### HNSW (Hierarchical Navigable Small World)

```
構造:
  ノード = ベクトル
  エッジ = 近いベクトル同士の関連

検索:
  グラフを辿って最近傍を探す
```

### 洞察

HNSW の構造は geDIG の知識グラフと同型！
- DG で確定されたエッジ = インデックスの更新
- グラフを辿る = 類似検索

## 6. GNN での介入可能性

### 問題提起

> HNSWのグラフ構造に介入はできるの？

### 検討

既存ライブラリ（FAISS等）：
- エッジを直接操作するAPIがない
- 内部グラフはブラックボックス

GNNライブラリ（PyTorch Geometric等）：
- グラフ構造を明示的に管理
- ノード/エッジの追加・削除が自由
- エッジに属性（重み、ラベル）を付けられる

### 結論

geDIG 的には GNN の方が親和性が高い。
ただし、迷路スケールなら networkx + 全探索で十分。

## 7. マスク検索の問題

### 洞察

> バナナ-黄色みたいな連想ってマスク検索だと思うんだ。

### マスク検索とは

```
通常: query = [0.5, 0.3, 0.2, ...]  全次元指定
マスク: query = [0.5, ?, 0.2, ...]  一部マスク
```

### 問題

> 生ベクトルならできるけど、indexだとできないんじゃないかって懸念した。

```
生ベクトル（全探索）:
  ✓ 検索時に任意のマスク/重みを適用可能
  ✗ O(n) で遅い

インデックス（FAISS等）:
  ✓ O(log n) で速い
  ✗ マスクを動的に変えられない
```

### 現状の迷路

WEIGHT_VECTOR を使って重み付き距離計算（実質的にマスク）。
生ベクトルでの全探索だから柔軟にできている。

## 8. 検索効率の問題（本質）

### 問題の再整理

> 検索ランキングつけるところが問題だったのかも。
> 類似度のランク付けで全グラフをベクトル検索していたのがネック

### 改善案

> クエリからすでに繋がってるエッジに登録された類似度をうまく使うデザイン

```
従来（全探索）:
  query → 全ノードと比較 → ランキング
  O(n)

新（エッジ探索）:
  query → 繋がっているエッジを見る → 類似度は記録済み
  O(隣接数)
```

### いつエッジに類似度を記録するか

ノード追加時（DG確定時）：
- この時だけ全ノードと比較（O(n)、一回だけ）
- 類似度をエッジ属性として記録
- 以降の検索はエッジを辿るだけ

### 「学習」と同じ構造

```
最初（経験なし）: エッジがない → 全探索が必要
経験を積む:       DGでエッジが増える → 類似度が記録される
習熟後:           エッジを辿るだけ → 高速
```

## 9. 行き止まり回避の実装

### 問題提起

> 課題は、行き止まりに行く選択をさせないこと。

### 洞察

> 分岐点には行き止まりとのDGエッジが生成されるはずでしょ？
> それと今の選択肢とのループ構造を検知するような感じ

### グラフ構造

```
(分岐点A, 東) ───DGエッジ───> (行き止まりB)
                                  │
                             outcome = -1
```

### ループ検知

```
分岐点A ─(東)→ 行き止まりB ─(戻る)→ 分岐点A
    └──────────────────────────────────┘
                  ループ！

行き止まり = 進めない = 戻るしかない = 同じ場所に戻る
```

### 実装ロジック

```python
def detect_deadend_loop(current_node, action, graph):
    action_node_id = (*current_node.position, action)

    if action_node_id not in graph.nodes:
        return False  # 未経験

    # このノードからのDGエッジを見る
    for neighbor_id in graph.neighbors(action_node_id):
        neighbor = graph.nodes[neighbor_id]['data']
        if neighbor.outcome < 0:
            return True  # 行き止まりに繋がる！

    return False
```

## 10. 設計原則のまとめ

### 検索の効率化

```
ノード追加時: O(n) で全比較 → エッジに類似度を記録
検索時:       O(隣接数) でエッジを辿るだけ
```

### 再認と想起の分離

```
再認: position index で exact match → confidence = 1.0
想起: エッジを辿る or 類似検索 → confidence < 1.0
```

### 行き止まり回避

```
エッジを辿って先を見る → outcome < 0 なら避ける
```

### グラフの役割

```
インデックス: 識別（同じ場所か？）
エッジ: 関連（何に繋がるか？） + 類似度（どれくらい近いか？）
ノード属性: 評価（良かったか悪かったか？）
```

### マスク検索とインデックスの両立

動的なマスク（重み）を使いたいが、インデックスは固定の距離関数。
→ 迷路スケールなら全探索で問題なし
→ 大規模時は「粗いフィルタ + 精密検索」の二段階

### 初見状態の扱い

エッジがない場所では全探索が必要。
→ 経験が増えるほど効率化される
→ 「学習」の自然な表現

### F値の具体的な計算
