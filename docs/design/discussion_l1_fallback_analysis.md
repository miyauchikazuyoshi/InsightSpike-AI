## 1. 問題提起

§19 のデバッグ報告で「L1フォールバック条件不在がバグ」と結論したが、
この論理接続は弱い。以下を整理する：

## 3. 代替仮説の検討

「L1フォールバック不在」以外に、CがBに負ける原因として考えられるもの：

### H1: L1候補パイプラインがpastQ候補を消失させている

**検証:**

L2パス（`build_ecand`、edges.py:56-147）の候補ソース:
```
1. mem候補: selection_candidates からメモリ起点の方向候補
2. pastQ候補: prev_graph の全 query ノードへのエッジ（include_qpast=True）
```

L1パス（`build_ecand_from_layer1`、edges.py:150-）の候補ソース:
```
1. L1候補: revisitノードの1-hop隣接ノードのみ
2. pastQ候補: **なし**
```

**L1が発火すると pastQ 候補が完全に消失する。**

pastQ候補とは: 現在のクエリノードから、グラフ上の全過去クエリノードへの候補エッジ。
これらは迷路の広範囲にわたる長距離ショートカットを geDIG に提供する。

25x25迷路で200 steps warmup 後、pastQ候補は数十〜数百個。
L1候補は revisit ノードの degree 個（典型的に2〜4個）。

→ **候補数・候補多様性が桁違いに異なる。**

**信頼度: 高。コードレベルで確認可能な事実。**

### H2: DG gate τ=1.0 が緩すぎて品質ゲートとして機能していない

propagated 値の分布（warmup未到達時）:
- novel: +0.2, revisit: -0.4, deadend: -1.0
- σ(-0.4/1.0) = 0.40（ほぼ中立、抑制が弱い）
- σ(+0.2/1.0) = 0.55（ほぼ中立、強化が弱い）

→ gate 値の range が 0.40〜0.55 → effective_score にほぼ影響なし。

**これはフォールバックの問題ではなく gate パラメータの問題。** だが、仮に τ を小さくしても
H1（pastQ消失）が解決されない限り、L1候補の多様性不足は残る。

**信頼度: 高。数値計算から確認可能。**

### H3: hash_index (L0) が誤検出している

VectorHashIndex の resolution=0.05 が粗すぎて、異なる位置を同一と判定する可能性。
→ これが起きると L1 に不正確な revisit ノードが渡される。

**検証:** F6 で C の eval_time 中央値が非常に低い（4.8-6.9ms）。
L1 は O(degree) で高速なので、L1 が頻繁に発火していること自体は整合的。
しかし L0 誤検出で「本来L2に行くべきステップ」がL1に回されている可能性はある。

**信頼度: 低〜中。** L0 の精度データがない。ただし θ_revisit=0.95 は厳しい閾値で、
誤検出率は低いはず。

### H4: threelayer コードパスに他のバグがある

L1 hit 時の `build_ecand_from_layer1` の出力が geDIG と非互換、等。

**検証:** ユニットテスト 29/29、後方互換 24/24 パス済み。
ただしこれらは「L1候補で geDIG が正しく評価を実行するか」のみ確認しており、
「L1候補で geDIG が有意義な改善を見つけられるか」は検証していない。

**信頼度: 低。** テストカバレッジ的にこの経路は検証済み。

### 仮説の重み付け

| 仮説 | 信頼度 | CがBに負ける説明力 |
|------|--------|-------------------|
| **H1: pastQ候補消失** | **高** | **非常に高** — 長距離候補の消失は構造的改善の機会を直接奪う |
| H2: τ=1.0 緩すぎ | 高 | 中 — gate が機能していなくても、候補が良ければ結果は出る |
| H3: L0 誤検出 | 低〜中 | 低 — θ_revisit=0.95 は厳しく、誤検出は少ないはず |
| H4: 他のバグ | 低 | 低 — テスト済みパス |

## 4. 真の原因メカニズム — pastQ消失仮説

### 4.1 因果連鎖

```
L1 発火（revisit + candidates ≥ 2）
  ↓
build_ecand_from_layer1 が呼ばれる（pastQ なし）
  ↓
geDIG に渡される Ecand = L1候補のみ（1-hop隣接、2〜4個）
  ↓
geDIG が評価できる候補エッジが局所のみ
  ↓
局所エッジの追加は ASP 改善が小さい → DG accepted = 0%
  ↓
構造的改善なし → 探索方針が変わらない
  ↓
同じエリアを繰り返し訪問 → β₁ 急増（冗長サイクル）
  ↓
AG 発火率低下（新情報なし） → 探索の多様性喪失
  ↓
ゴール未到達（500 steps）
```

### 4.2 B（legacy）が成功する理由

```
L2 常時使用
  ↓
build_ecand が呼ばれる（pastQ あり）
  ↓
Ecand = mem候補 + pastQ候補（数十〜数百個）
  ↓
geDIG が長距離ショートカットを評価できる
  ↓
ASP 改善の機会がある → 探索方針が適応的に変化
  ↓
多様な探索 → AG 発火率維持 → ゴール到達
```

### 4.3 seed 1 で C が成功する理由

seed 1 では C が 146 steps で成功（B: 250 steps）。なぜ seed 1 だけ？

- seed 1 の AG 発火率: C(57.5%) > B(45.2%)
- seed 1 の node_growth: C(3.52) > B(2.89)
- seed 1 の β₁: C(32) < B(85)

仮説: seed 1 の迷路トポロジーでは、L1の局所候補だけでゴールに到達できるパスが
たまたま存在していた。つまり L1 の scope でも十分な seed では C が有利（L1 の高速性
が活きる）。しかしこれは seed 依存であり、汎用的には L1 scope の限界が C を害する。

### 4.4 主張の変遷

| 段階 | 主張 | 問題 |
|------|------|------|
| 初期 | L1候補の「品質」が低い | 「品質」の定義が曖昧 |
| §4 時点 | L1候補の**多様性・スコープ**が狭い（pastQ消失） | 因果は特定できたが修正案が応急処置的 |
| §8 で修正 | **L1の1-hop制限がグラフインデックスを活かしきれていない** | → §8 参照 |

## 5. 「L1フォールバック不在はバグか？」

### 5.1 厳密にはバグではない

コードは設計通りに動作している：
- L1 が候補を返す → `len(cands) >= min_layer1` → L1 採用
- L2 パスはスキップ

**設計仕様通りの動作。バグではなく設計の限界。**

### 5.2 設計の暗黙の前提が誤っていた

三層検索の設計は以下を暗黙に仮定していた：

> **前提A**: L1候補は L2候補の subset として十分な品質を持つ
> **前提B**: L1でL2をスキップすることで計算量を削減しても、判断品質は維持される

**前提A が誤り。** L1候補はL2候補の subset ですらない。L1 と L2 は候補生成の
メカニズムが完全に異なる：

| | L1 | L2 |
|---|---|---|
| 候補ソース | グラフ隣接 (1-hop) | メモリ全体 + pastQ |
| 候補の性質 | トポロジー的近傍 | ベクトル空間的近傍 + 長距離 |
| pastQ | なし | あり（全過去クエリ） |
| 典型的候補数 | 2〜4 | 数十〜数百 |

L1 が L2 を「代替」するのではなく、**L1 は L2 の重要な部分（pastQ）を切り捨てて
いる**。

### 5.3 修正の方向性（§8 で再評価）

当初の修正案：

```
[レベル1] フォールバック条件追加
[レベル2] L1 に pastQ 併合      ← 当初「本質的修正」と判断
[レベル3] Multi-Hop Walker
```

**→ §8 で優先度が逆転。詳細は §8.3 参照。**

## 8. L1 の本質再定義 — グラフインデックスとしての L1

### 8.1 L1 の誤った理解と正しい理解

§4-5 では L1 を「局所高速検索」と位置づけ、pastQ（長距離候補）の消失を
根本原因とした。しかしこの分析は **L1 の本質を見誤っていた**。

| | 誤った理解 | 正しい理解 |
|---|---|---|
| L1の役割 | 局所的で高速な検索（O(degree)） | **グラフインデックスを使った構造的検索** |
| L2との関係 | L1 ⊂ L2（L1はL2の高速版） | L1 ≠ L2（異なるインデックス戦略） |
| 長距離候補の確保 | pastQで補う必要がある | **グラフ走査自体が長距離に到達する** |
| L1の速度利点 | O(degree) vs O(N) | **インデックス構造によるガイドあり検索** |

### 8.2 グラフはインデックスである

L2（全メモリソート）は **構造を持たないブルートフォース検索**。
全ノードのベクトル距離を計算してソートする。

L1（グラフ走査）は **事前計算済みインデックスを使った構造的検索**。
グラフのエッジに蓄積された情報が検索をガイドする：

| エッジ/ノード属性 | 役割 | 計算タイミング |
|-------------------|------|--------------|
| attention | 利用頻度・鮮度。「よく使う道」を示す | 毎ステップ更新（decay/boost） |
| propagated | 方向の価値。「この先にゴールがある/行き止まり」 | Sleep相で焼き込み |
| トポロジー | 実際の遷移関係。「ここからどこに行けるか」 | 探索時に構築 |

これらは**全て事前計算済みのキャッシュ**であり、
L1がグラフを歩くとき、各エッジの属性を読むだけで判断できる。

L2はこれらのインデックスを一切使わない。ベクトル距離だけで候補を選ぶ。

### 8.3 pastQ vs Multi-Hop Walk — ブルートフォース vs 構造的検索

pastQ の仕組み（`build_ecand` lines 127-142）:
```
全ノード走査 → node_type == "query" のフィルタ → 候補エッジ生成
```

これは **インデックスなしの全走査**。構造情報（attention, propagated）を
一切使わない。O(V) で全過去クエリを候補にする。

Multi-Hop Walker の仕組み（§18.2 設計）:
```
revisit ノード → attention 順に priority queue → DG gate で枝刈り → 候補発見
```

これは **グラフインデックスに沿った構造的探索**。
attention チェーンが高い方向に歩き、propagated が負の方向を枝刈りする。

| | pastQ (brute force) | L1 multi-hop (graph index) |
|---|---|---|
| 計算量 | O(V) 全走査 | O(walked) attention枝刈り |
| 候補品質 | 無差別（全過去クエリ） | attention × DG gate でガイド |
| 長距離到達 | 常に可能（全ノード走査） | attention チェーンが繋がっていれば到達 |
| Sleep活用 | なし | propagated で価値判断 |
| スケーラビリティ | O(V) — ノード数に比例して劣化 | O(walked) — グラフ密度に依存、枝刈りで制御 |

**Multi-Hop Walker が proper に動けば、pastQ は不要になる。**

pastQ が提供していた「長距離候補」は、グラフ走査が構造的にカバーする。
しかもブルートフォースではなく、attention + DG gate でガイドされた形で。

### 8.4 なぜ pastQ 併合が「応急処置」なのか

pastQ を L1 に追加する案（§5.3 レベル2）を再検討する：

```
L1パス + pastQ 併合:
  L1候補: attention-guided（構造的） → 局所高品質
  pastQ:  brute-force（非構造的）    → 大域無差別

→ 構造的検索 + 非構造的検索のキメラ
→ L1の設計原則（構造的検索で L2 を超える）と矛盾
```

L1 に pastQ を足すのは、「インデックスが不完全だからフルスキャンで補う」
に等しい。これはインデックスを修正するのではなく回避している。

**正しいアプローチ: インデックス自体を修正する（1-hop → multi-hop）。**

### 8.5 1-hop 制限が全ての元凶

現在の L1 失敗の因果連鎖を改めて整理する：

```
真の原因: L1 が 1-hop しか歩かない
  ↓
グラフインデックスの到達範囲が degree 個に限定
  ↓
長距離候補が出ない（pastQ に相当する候補が生成されない）
  ↓
geDIG が局所エッジしか評価できない
  ↓
構造改善なし → ループ → β₁急増 → AG低下 → 失敗
```

pastQ 消失（§4）は**症状**であり、原因は 1-hop 制限。
フォールバック条件不在（初期仮説）は**悪化要因**であり、原因ではない。

Multi-Hop Walker は 1-hop 制限を直接解消する。attention チェーンを
辿って遠方ノードに到達することで、pastQ のブルートフォースを
構造的検索に置き換える。

### 8.6 L1 が L2 より「速く確実」になる条件

L1 が L2 を正当に超えるための条件：

| 条件 | 必要性 | 現状 |
|------|--------|------|
| Multi-Hop Walk | **必須** | 未実装（1-hop のみ） |
| attention チェーンの連結性 | 高い | Sleep + decay で自然に形成（要検証） |
| propagated の品質 | 中 | warmup 未到達時は弱い（novel:+0.2 程度） |
| 質的フォールバック | 保険 | 未実装 |

**Multi-Hop Walker が実装されれば：**

- Sleep 到達済み: propagated で即座に枝刈り → O(少数hop) で高品質候補
- Sleep 未到達: attention チェーンを辿って直接確認 → pastQ 不要
- attention チェーン切断: 候補不足 → フォールバック → L2

L2 はこれらの構造情報を一切使えない。
**グラフインデックスが正しく機能すれば、L1 は L2 より速く、かつ精度も高い。**

## 9. 修正された優先順位

### 9.1 優先順位（最終版）

```
[P0] Multi-Hop Walker（graph_walker.py 改修）
     → 1-hop → attention-guided BFS + DG gate 枝刈り
     → L1 のグラフインデックス機能を本来の形にする
     → これが根本修正。pastQ 併合は不要になる可能性が高い

[P1] 質的フォールバック（search_engine.py 条件追加）
     → attention チェーンが途切れた場合の安全弁
     → max(dg_gate) < threshold → L2 fallback

[P2] τ パラメータ調整
     → 1.0 → 0.3 程度
     → propagated の微小差を増幅

[保留] pastQ 併合
     → P0 実装後に C ≥ B が達成されれば不要
     → 達成されなければ応急処置として検討
```

### 9.2 検証戦略

```
Step 1: P0（Multi-Hop Walker）のみ → B vs C_multihop
        - pastQ なしで C ≥ B が達成されるか
        - attention チェーン到達範囲の確認

Step 2: P0+P1（+ フォールバック） → 安定性向上の確認
        - チェーン切断時に L2 で救済されるか

Step 3: P0+P1 で C < B の場合のみ pastQ 併合を検討
```

### 9.3 データ補強（引き続き必要）

1. **search_layer_used_series**: ablation 出力に追加
2. **L1 walk 到達範囲**: multi-hop 実装後、何 hop 先まで到達するか計測
3. **attention チェーン連結性**: prev_graph 上で attention > θ のエッジだけを辿った場合のグラフ直径

## 10. 結論（最終版）

### 分析の変遷

| 段階 | 原因の主張 | 修正案 |
|------|-----------|--------|
| 初期（§19） | フォールバック条件不在 | フォールバック追加 |
| §4-5 | pastQ 候補パイプライン消失 | pastQ 併合 |
| **§8（最終）** | **L1 の 1-hop 制限がグラフインデックスを無力化** | **Multi-Hop Walker** |

### 最終結論

> **L1 の失敗原因は「フォールバック不在」でも「pastQ 消失」でもない。**
> **1-hop 制限によりグラフインデックスの到達範囲が graph.degree 個に限定され、**
> **L1 の構造的検索能力が発揮されないことが根本原因。**
>
> pastQ（ブルートフォース全走査）は L2 の補助機構であり、
> L1（構造的検索）がグラフを proper に歩ければ不要になる。
>
